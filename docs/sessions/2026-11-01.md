## [11:20] pr-review-rework-t03: the `changes_requested` status

- `factory/db.py`: `changes_requested` joined `STATUSES` and `("reviews_addressed", "INTEGER")` the
  `tasks` migrations, so older databases get the column on open and `db.update` accepts both.
- `factory/cli.py`: `_refresh` now reads reviews (via `reviews.fetch`/`reviews.requests`) for every
  open task whose PR head is the factory's candidate, with the precedence merged/closed → conflict →
  requested changes → CI. A requesting review marks the task `changes_requested` (note names the
  reviewers and `` `factory run TASK` ``), a cleared request returns it to `pr_open`, a review on a
  head someone else pushed sends it back to `pr_open` (reviews left to them), and a gh failure leaves
  the review status alone. `_adopt` records the latest review id at take-up as `reviews_addressed`,
  `cmd_run_one` refuses a `changes_requested` task without `--force`, and `cmd_requeue` leaves it alone.
- `factory/observe.py`: `↺` glyph, a `changes requested` counter, the detail line, and `render_top`'s
  `prs`/`live` status lists now cover the new status.
- `factory/scheduler.py`: `summary` lists a `changes_requested` task like `ci_failed` (URL + note);
  dependents already wait on it (`waits for TASK (changes_requested)`), and plan runs skip it until the
  rework lands.
- `factory/stack.py`: `restack` moves a stacked `changes_requested` PR like a `pr_open` one and keeps
  its status and note.
